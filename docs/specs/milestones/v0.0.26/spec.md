# v0.0.26 — Closing a milestone: `milestone close` and the milestone index

v0.0.25 gave the Harness `milestone new` and `milestone check`. A milestone is still closed by hand: nothing records that it shipped, nothing ties the manifests to the closed version, and no file lists the milestones that shipped. GSD closes a milestone with an audit, a newest-first `MILESTONES.md` entry and a tag ([research-synthesis.md](../v0.0.25/research-synthesis.md), section 3), and its tag is created before the commit that removes the requirements file, so tag and archive disagree. This milestone adds the close as a gate that writes one thing: an index entry. It never tags, moves or deletes. The scope was chosen by the Jev judge from [brief.md](brief.md) ([decisions.md](decisions.md)).

## Requirements

- R1 `milestone close [VERSION] [--date YYYY-MM-DD] [--root DIR] [--dir RELDIR]` in `inonu_harness/milestones.py` (`close_milestone(root, directory, version=None, date=None)`), reachable as `python -m inonu_harness milestone close ...` and `python -m inonu_harness.milestones close ...`, with the same containment rules as `new` and `check` (R2 of v0.0.25). Without `VERSION` it closes the highest in-scheme milestone folder. Without `--date` it uses today's date; the date must be a real calendar date written `YYYY-MM-DD` and not later than today. `VERSION` is written without a leading `v`.
- R2 The close is refused (exit 1, nothing written, one fixed line per reason on stderr, no absolute path) unless all of these hold: the folder exists; the check of that folder finds no error; `checkpoint.md` exists and is a regular file inside the root, names `v<version>` in its first non-empty line, has a line that starts with `Status:` and has `## Verification` and `## Limits` headings; the manifests state exactly this version (a project with no manifest that states a version is not held to this; manifests that disagree, are outside the scheme or state another version refuse the close, with the message to bump them first); the version is higher than every version already in the index; the version is not already in the index; the index, if it exists, has no lint error.
- R3 The index is the file `MILESTONES.md` inside the milestones directory. Its format is the heading `# Milestones`, a one-line description, and one entry per closed milestone, newest first: `## v0.0.26 — Title (Shipped: 2026-10-27)` followed by the list items `- Requirements: N`, `- Deferred: N` and `- Folder: [v0.0.26](v0.0.26/)`. The title is the text after the dash in the first heading of `spec.md` and the part `— Title` is left out when there is none.
- R4 Writing: the new entry is placed before the first existing entry (or the file is created with the header). The file is written to a temporary file in the same directory and put in place with `os.replace`, so a failure leaves the old index untouched and no temporary file behind. An existing index larger than 1 MiB, not UTF-8, or whose path resolves outside the root is refused. `close` creates nothing else, moves nothing, deletes nothing and does not touch git. It prints `{"schema_version": 1, "version", "index": "<relative path>", "entry": "<the entry text>"}` with sorted keys.
- R5 Deferred items: the list items under a `## Deferred` or `## Deferred items` heading of `checkpoint.md` are counted into `- Deferred: N`. Each item must give a reason, written after an em dash or a colon; an item without one refuses the close (`deferred_without_reason`). The section is optional.
- R6 `milestone check` also: (a) reports `checkpoint_version_mismatch` (error) for a checked milestone whose `checkpoint.md` does not name its own `v<version>` in its first non-empty line, so a checkpoint copied from another milestone is caught; (b) when `MILESTONES.md` exists in the milestones directory, lints it whatever `--from` says, as an entry with the version `index`, with the rules `index_malformed` (a line that is not part of the format), `index_order` (versions not strictly descending), `index_duplicate`, `index_link_broken` (the folder does not exist or is not a directory), `index_date_invalid` and `index_date_order` (a date earlier than the date of an older entry). All are errors.
- R7 Exit codes of `close`: 0 written; 1 refused; 2 invalid input (a missing root, a bad `--dir`, a version or date that is malformed). A `VERSION` that has no folder is exit 2 when the milestones directory exists.
- R8 The existing rules of v0.0.25 keep their meaning, and a folder just created by `milestone new` still passes `check`. The `check` step of this repository needs no change.
- R9 Tests cover:
  - `close`: each refusal of R2 with a fixed message (missing checkpoint, wrong version in the first line, no `Status:`, no `## Verification`, no `## Limits`, a check error, manifests that state another version, that disagree or are outside the scheme, a version not above the index, a version already closed, a malformed index), the success case, a project without manifests, the first entry creating the file, a second entry going before the first, the title and the requirement count in the entry, `--date` validation (`2026-02-30`, `26-1-1`, an empty value), the default date, containment (a link out of the root on the index path, via a patched `resolve` where links are impossible), an oversized or non-UTF-8 index, atomic replacement (a failing `os.replace` leaves the old index and no temporary file), and no write on refusal;
  - deferred items: counted, with reasons, without reasons, a different heading level, a deferred section inside a fenced block or an HTML comment;
  - `check`: checkpoint identity at its boundary (first non-empty line, `v0.0.1` against `v0.0.10`), no checkpoint at all, an index in every state of R6 and a clean one, the index linted with `--from`, and exit codes;
  - the repository: `check_milestones` on this repository with `start="0.0.9"` has no error, and a closed copy of the v0.0.25 folder in a temporary project is accepted.
- R10 Docs: `docs/milestones.md` gains the close, the index format, the checkpoint skeleton it requires and the new rules; the README, the CHANGELOG 0.0.26, the Portuguese paragraph in `docs/sdd-workflow.md` and a bullet in the skill carry the command to every project; `docs/versioning.md` says that the manifests are bumped before the close. Version 0.0.26 in the three manifests.
- R11 This repository closes v0.0.25 with the command once the code passes review, which creates its index. The close needs the manifests to state 0.0.25, so the three manifests are set back to 0.0.25 for that one command and restored to 0.0.26 afterwards; the order of a real project is bump, checkpoint, close, then the next milestone.

## Out of scope

Backfilling the index for earlier milestones, git tags, moving or archiving folders, deleting files, a retrospective file, bumping the manifests, a task status column, append-only gap tasks, pause and resume, and any change to `sdd audit`.
