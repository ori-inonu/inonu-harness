# v0.6.0 plan — D01/D02 offline evaluation design

This plan captures the proposed design only. The current authorized increment is documentation; it does not create or execute fixtures, modify code, call live models or services, install or adopt tools, or implement a router.

1. **D01 corpus proposal:** define five sanitized case intents and expected eight-stage traces in [spec.md](spec.md). Use existing baseline and SDD-context fixtures only as local format references.
2. **D02 rubric proposal:** define mandatory per-fixture pass/fail gates, evidence references, the sole justified `N/A` case, a complete case-level claim ledger for material claims in `input_intent`, all eight stages, expected/observed outcomes, and gate evidence, plus the separate qualitative note record in [spec.md](spec.md). Preserve the runner's limits: it records supplied acceptance outcomes and does not judge traces.
3. **D03 candidate-scope decision:** select whether any research candidate practice merits a later offline evaluation. Keep this open; the current receipts and design do not choose a treatment or authorize implementation.
4. **Later authorized fixture work:** only after D03 and explicit authorization, create the five separate case records. Tests must validate exact claim-ledger coverage for `input_intent`, each expected/observed stage, expected/observed outcomes, and every gate evidence reference. Include negative cases where an input claim or gate-evidence claim is omitted, as well as missing, duplicate, orphaned, unclassified, or unresolved required references. Validate those and the case expectations before computing gate outcomes. Then build a complete in-memory baseline v1 mapping with every required field before calling `run_fixture(...)`. A CLI-seam test writes that same valid mapping to a temporary JSON file and invokes `baseline run`; case records are not passed directly to the baseline parser. Keep justified `N/A` reasons outside the baseline v1 acceptance array; do not compare measured duration or Python/component versions.
5. **Later offline recording and review:** compare observed trace entries and material claim ledgers with frozen expectations, pass computed gate outcomes through the existing baseline runner, retain evidence per case, and keep reviewer notes separate. Do not aggregate scores or claim live-agent quality or productivity.

The later tasks in [tasks.md](tasks.md) are planned and blocked until their stated dependencies and authorization are satisfied. This plan does not claim evaluation completion or convergence.
