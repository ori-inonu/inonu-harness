# v0.0.24 research: official documentation and leading engineers

Date: 2026-10-26. Method: one reader per source group fetched the primary pages with WebFetch and wrote practices in its own words; a second, independent reader then re-fetched every cited page and judged each practice and each comparison with Inonu against the description of Inonu it was given and, where it could, the repository. Every reader and verifier was a Haiku-class model. No human has read the pages, so a practice marked supported means that a second model found the page saying it, not that the owner confirmed it.

The readers' own lists of candidate gaps are not copied here: the verifiers found that several of them describe things Inonu already has (an iteration cap in the loop runner, hash-based re-trust of the hook config, a failure reason on a blocked stop). The gaps that survive are in [research-gaps.md](research-gaps.md).

### Practices

- **AN-01** (harness, supported) Start a long run with a separate initializer step that creates an init script, a progress log and a first git commit. Each later session makes one increment, commits descriptively and leaves structured notes. Track features in a machine-readable list where every item starts as failing; agents change only the status flag, and only after end-to-end checks. The article prefers JSON because models damage Markdown less. Source: <https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents>, Environment management (Feature list, Incremental progress); Getting up to speed.
- **AN-02** (verification, supported) A unit of work counts as done only when external checks pass, not when the agent says so. The article names two failure modes: declaring the project complete too early, and marking features as passing without proper end-to-end testing. It recommends testing as a human user would, through browser automation, since code reading misses bugs. Source: <https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents>, Agent failure modes and solutions (table); Environment management > Testing.
- **AN-03** (evals, supported) Separate the evaluator from the generator instead of self-review. A default model was a weak QA agent that talked itself into approving bugs. Make subjective criteria concrete, calibrate the grader with few-shot examples that have score breakdowns, and fail a unit when any hard threshold fails. Before work, the generator proposes what it will build and how success is verified, and the evaluator negotiates until both agree. Source: <https://www.anthropic.com/engineering/harness-design-long-running-apps>, 02 Frontend design: making subjective quality gradable; 03 Scaling to full-stack coding (sprint contract step).
- **AN-04** (loop, supported) Bound the loop with stopping conditions such as a maximum iteration count. Agents should check real results from the environment at each step, and pause for human feedback at checkpoints or blockers. Human review stays important for coding work even when automated tests pass. Source: <https://www.anthropic.com/research/building-effective-agents>, Building blocks, workflows, and agents > Agents.
- **AN-05** (loop, supported) Use the simplest solution that works and add agentic complexity only when it is needed, since agents trade latency and cost for performance. Call LLM APIs directly before adopting a framework, because frameworks can hide prompts and responses. Compose patterns only as needed: prompt chaining with programmatic checks between steps, routing, parallelization, orchestrator-workers and evaluator-optimizer, which works best with clear evaluation criteria. Source: <https://www.anthropic.com/research/building-effective-agents>, When (and when not) to use agents; When and how to use frameworks; Building blocks, workflows, and agents.
- **AN-06** (other, supported) Design tools for agents as carefully as prompts. Build a few tools for high-impact workflows instead of wrapping every endpoint, consolidate chained calls, avoid overlapping tools, and namespace by service and resource. Use unambiguous parameter names, strict schemas and explicit example usage, and make mistakes hard, for example by requiring absolute paths. Return human-readable names instead of opaque IDs, offer concise and detailed response modes, paginate and truncate with sensible defaults, and write error messages that steer the next call. Source: <https://www.anthropic.com/engineering/writing-tools-for-agents>, Principles for writing effective tools (Choosing the right tools; Namespacing; Returning meaningful context; Optimizing for token efficiency; Prompt-engineering tool descriptions).
- **AN-07** (context, supported) Treat context as a finite attention budget and keep the smallest set of high-signal tokens. Pitch system prompts at the right altitude, avoiding brittle hardcoded logic and vague guidance. Load detail just in time through lightweight references such as paths and queries, and sometimes preload a hybrid set. For long-horizon work use compaction (maximize recall first, then trim), structured notes kept outside the window, and sub-agents that return condensed summaries. Over-aggressive compaction can drop subtle details. Source: <https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents>, 3. The anatomy of effective context; 4. Context retrieval and agentic search (context engineering for long-horizon tasks).
- **AN-08** (hooks, supported) Hook exit-code contract: exit 0 with no JSON makes no decision; exit 2 blocks on events that can block and sends stderr as the reason; any other non-zero exit, including 1, is non-blocking. Set a failure policy (onFailure block) so that timeouts, non-0/2 exits, HTTP errors and invalid output can block; defaults are 600 seconds for command hooks and 30 for prompt hooks. The reference lists 33 lifecycle events, including PreToolUse for gating before a tool runs. It warns that the if filter is best effort and that hard allow or deny rules belong in the permission system, and that silence is not approval. Source: <https://code.claude.com/docs/en/hooks>, Hook events; Exit codes; Timeouts; Failure handling; Security and trust.
- **AN-09** (skills, supported) Load skills progressively: only descriptions sit in context at startup, the full SKILL.md enters on invocation, and supporting files load only when referenced. Put the key use case first in the description, keep SKILL.md under 500 lines and move reference material to linked files. Use disable-model-invocation for side-effecting workflows such as deploys, and user-invocable false for background knowledge. allowed-tools pre-approval lasts only for the invoking turn. Source: <https://code.claude.com/docs/en/skills>, SKILL.md structure; Progressive disclosure; Invocation; Tool permissions.
- **AN-10** (harness, supported) Subagents run in their own context window with their own system prompt, tool access and permissions, and return condensed results to the main conversation. Use one for verbose side tasks, restrict tools with an allowlist, and set a model per agent. Subagents do not inherit parent conversation or skills unless preloaded. Defaults cap nesting at three layers and concurrency at 20. The docs warn that many long subagent reports can still consume main context. Source: <https://code.claude.com/docs/en/sub-agents>, What subagents are; File format; Context and inheritance; Subagents versus the main conversation and skills.
- **AN-11** (safety, supported) Permission rules are evaluated in order: deny, then ask, then allow; the first match decides, and specificity does not change the order. A narrower allow cannot carve an exception out of a broad deny. Bash rules match command text and are not a security boundary around the program. CLAUDE.md and memory are loaded as context, not enforced configuration; to block an action regardless of the model, use a PreToolUse hook. Keep CLAUDE.md under about 200 lines and move procedures to skills or path-scoped rules. Source: <https://code.claude.com/docs/en/permissions>, Permission system (rules evaluated in order); Bash rule limits; memory page 'CLAUDE.md vs auto memory' and 'Size'.
- **AN-12** (safety, supported) Use OS-level sandboxing for agent commands: macOS uses Seatbelt, Linux and WSL2 use bubblewrap with a proxy. Network is default-deny, with an allowedDomains list that starts empty; filesystem writes are limited to the working directory and protected paths stay write-denied. Reads are broadly allowed by default, so credential paths such as the SSH directory need explicit read denies. Built-in file tools, hooks and MCP servers run outside the sandbox, and native Windows has no sandbox, so WSL2 is needed. Disable retry-unsandboxed to close an escape hatch. Source: <https://code.claude.com/docs/en/sandboxing>, Filesystem isolation; Network isolation; Limitations; Escape hatches and weakening settings.
- **AN-13** (evals, supported) Evaluate with realistic multi-step tasks drawn from real data and workflows, each paired with a verifiable outcome, and avoid verifiers so strict they reject correct answers over formatting. Record accuracy, runtime, tool calls, tokens and errors, and have agents output reasoning with tool calls. Analyze transcripts for confusion, redundant calls and parameter errors, and use held-out test sets to detect overfitting. Source: <https://www.anthropic.com/engineering/writing-tools-for-agents>, How to write tools (Building a prototype; Running an evaluation; Iterate with agents).
- **AN-14** (harness, supported) Each harness component encodes an assumption about what the model cannot do alone, so stress-test those assumptions when the model changes. The authors removed components one at a time, which worked better than a radical cut: the sprint construct was dropped for a newer model while the planner was kept, because without it the generator under-scoped. Context resets were later dropped in favor of compaction when a newer model stopped showing context anxiety. Source: <https://www.anthropic.com/engineering/harness-design-long-running-apps>, Simplifying as models improve; Scaling to full-stack coding > Removing the sprint construct.

### Practices

- **P01-agents-md-chain** (context, supported) Codex builds an instruction chain once per launched session: one global file from the Codex home (an override file wins over the standard one), then at most one file per directory from the project root down to the working directory. Deeper files are concatenated later and so take precedence. Combined content is capped at 32 KiB by default (project_doc_max_bytes); once the cap is reached no further files are added. Empty files are ignored. Source: <https://learn.chatgpt.com/docs/agent-configuration/agents-md>, Discovery and merge; Size limits and config keys.
- **P02-agents-md-upkeep** (memory, supported) Keep AGENTS.md short and accurate, add a rule only after a repeated mistake, and move task-specific detail into separate markdown files when it grows. When the same mistake recurs, ask for a retrospective and update the file. Recommended content includes build, test and lint commands, the preferred package manager, and confirmation before adding production dependencies. Source: <https://learn.chatgpt.com/guides/best-practices>, Durable guidance with AGENTS.md; see also Recommended content in the AGENTS.md page.
- **P03-done-when-verification** (loop, supported) Give each task a goal, relevant context, constraints, and a 'Done when' completion condition. The agent can verify its work only if it knows the build, test, lint and type-check commands, so state them in the prompt or AGENTS.md, then have it run the checks and review the diff before finishing. Source: <https://learn.chatgpt.com/guides/best-practices>, Context and prompts; Verification and code review.
- **P04-plan-first** (loop, supported) For complex or ambiguous work, plan before editing. The page recommends a plan mode that gathers context and asks clarifying questions as the default, and a plan or execution-plan file for longer multi-step work. Source: <https://learn.chatgpt.com/guides/best-practices>, Planning difficult tasks.
- **P05-sdk-loop-stop** (loop, supported) The SDK loop calls the model each iteration. Output with text and no tool calls is final and ends the loop; a handoff switches the active agent; tool calls are executed, their results appended, and the loop repeats. Turns (model calls) are capped by max_turns, which raises an error when exceeded unless an error handler returns a controlled fallback. Source: <https://openai.github.io/openai-agents-python/running_agents/>, The Agent Loop; Final Output; Turn Limit (max_turns).
- **P06-guardrail-scope-mode** (safety, supported) Place guardrails by scope: input checks run only on the first agent, output checks only on the agent that produces the final output, and tool checks wrap each guarded function-tool call (input before execution, output after). Handoffs and hosted tools are not covered. Parallel mode (the default) lowers latency, but the agent may already have spent tokens or run tools when a check trips; blocking mode finishes the check before the agent starts. Blocked-message placeholders must not carry sensitive data. Source: <https://openai.github.io/openai-agents-python/guardrails/>, Workflow boundaries; Execution modes; Tool guardrails; Recommendations.
- **P07-approval-interrupt** (safety, supported) A tool marked as needing approval is not executed; the run returns pending interruptions and a serializable state. The application approves or rejects each item and resumes from that state, possibly much later. Pause before side effects such as cancellations, edits, shell commands and sensitive MCP actions. Give reviewers only the exact proposed action and needed context, log decisions and outcomes, and fail closed when review times out or is unavailable. Source: <https://developers.openai.com/api/docs/guides/agents/guardrails-approvals>, When to Require Human Approval; How Approvals Work in the SDK; Tool-Risk Classification Recommendations.
- **P08-sandbox-and-approval-layers** (safety, supported) Codex separates two controls: the sandbox sets what commands can technically read and write (read-only, workspace-write, danger-full-access), and the approval policy sets when the agent must stop and ask. Protected paths (.git, .agents, .codex, .aws) stay read-only even inside writable roots. Network is off by default in workspace-write; when enabled it follows allowlist-first domain rules where deny overrides allow, and loopback or private-network destinations stay blocked unless excepted. Source: <https://learn.chatgpt.com/docs/agent-approvals-security>, Sandbox modes; Approval policies; Network access; Protected paths; How approvals interact with the sandbox.
- **P09-hooks-lifecycle-trust** (hooks, supported) Codex hooks run at lifecycle events (session start, prompt submit, pre- and post-tool use, permission requests, pre- and post-compaction, subagent start and stop, turn stop, session end). Exit 0 continues; exit 2 blocks on events that support blocking, with stderr as the reason; JSON output can deny or rewrite a tool call, and a Stop hook can keep the turn going. Non-managed hooks must be reviewed and trusted before they run; trust is keyed to a hash, so a changed hook is skipped until re-trusted; project-local hooks load only when the project config layer is trusted. The docs call tool hooks a useful guardrail, not a complete enforcement boundary. Source: <https://learn.chatgpt.com/docs/hooks>, Lifecycle events; Exit codes and JSON output; Trust and review; Safety and security recommendations.
- **P10-skills-progressive-disclosure** (skills, supported) A skill is a folder with a SKILL.md whose frontmatter requires name and description. At startup only name, description and path load, in a list capped at about 2% of the context window (8,000 characters when the window size is unknown); the full body loads only when the skill is selected. Write the description as the trigger: main use case and keywords first, plus when the skill should not apply. Keep one job per skill, default to instructions only, add scripts only for deterministic behavior, and test that prompts trigger the intended skill. Source: <https://learn.chatgpt.com/docs/build-skills>, SKILL.md Format; Progressive Disclosure; Writing Descriptions and Scoping; Scripts and References; Testing and Evaluation.
- **P11-sessions-state-trust** (memory, supported) An SDK session stores conversation items between runs: the runner loads prior history before a run and saves the new items after it. Retrieval can be limited to the most recent N items, and compaction can be automatic or manual. The session ID only selects history; it does not authenticate or authorize anyone, so the application must control access to sessions, database files and backups. The SQLite session trusts its database, skips undecodable rows silently, and does not detect external edits, deletions or replay. Source: <https://openai.github.io/openai-agents-python/sessions/>, Purpose and Core Behavior; History Shaping, Limits, and Compaction; Sensitive Data and Retention.
- **P12-handoff-context-filters** (harness, supported) A handoff appears to the model as a tool named after the target agent. Its typed input carries small model-generated metadata and does not replace application state, which belongs in the run context. Validate parsed handoff input at the start of the callback before any side effect, because the enabled-check runs before the model supplies arguments. Choose the history the receiver sees with an input filter (full history by default); tool content already copied into messages is not redacted by stripping tool items. Use one handoff per destination so the model chooses. Source: <https://openai.github.io/openai-agents-python/handoffs/>, How Handoffs Appear to the Model; Handoff Callbacks; Handoff Inputs; Input Filters and Conversation History; Recommended Patterns.
- **P13-tracing-defaults-redaction** (verification, unsupported) The SDK traces each run by default: agent runs, model generations, function tool calls, guardrail checks and handoffs. Generation and function spans record inputs and outputs, and trace_include_sensitive_data defaults to true, so sensitive data reaches traces unless turned off. Processors act independently, so redaction must sit inside the single exporter that sends data; a redactor placed before another exporter does not guarantee redacted export. Workers should flush traces explicitly before exiting. Source: <https://openai.github.io/openai-agents-python/tracing/>, Default Tracing; Sensitive Data; Redaction Before Export; Long-Running Workers and Immediate Exports.
  - Verifier: Supported: tracing is on by default across runs, generations, function calls, guardrails and handoffs; generation and function spans record inputs and outputs; trace_include_sensitive_data defaults to True; processors act independently, so redaction belongs inside the single exporter that sends data (openai.github.io/openai-agents-python/tracing/). Contradicted: 'Workers should flush traces explicitly before exiting.' Under 'Long-running workers and immediate exports' the default batch processor does a final flush at process exit, and flush_traces() is optional for an immediate delivery guarantee ('You can skip this call when the default export latency is acceptable'). A targeted re-fetch confirmed this.
- **P14-trace-grading-then-datasets** (evals, supported) Debug with traces first: grade representative multi-step traces against structured criteria, such as whether the agent chose the right tool, whether a handoff happened when it should, whether an instruction or safety policy was broken, and whether a prompt or routing change improved end-to-end behavior. Once criteria are defined, move to datasets and eval runs to repeat comparisons over time. The page does not separate step-level from end-to-end evaluation and gives little regression-testing detail. Source: <https://developers.openai.com/api/docs/guides/agent-evals>, Start with traces when debugging; Move to datasets and eval runs for repeatability; Gaps in this content.

### Practices

- **G01** (loop, supported) Loop control is deterministic: a workflow agent, not a model, runs the sub-agents in fixed order and repeats the cycle. The loop never decides on its own when to stop, so the builder must set an iteration cap as a safety limit and also define an explicit exit path. Source: <https://adk.dev/agents/workflow-agents/loop-agents/>, How iterations run; Termination conditions.
- **G02** (verification, unsupported) Exit the loop only on a checkable condition: a sub-agent raises an escalate flag when an exact sentinel or deterministic check passes. Give the critic concrete completion criteria and skip purely subjective critique, so the loop converges instead of revising indefinitely. Source: <https://adk.dev/agents/workflow-agents/loop-agents/>, Termination conditions; Recommended practices.
  - Verifier: The escalate flag and the exact sentinel 'No major issues found.' appear only in example code. The prose describes a STOP signal 'when the document reaches a satisfactory quality level', which is subjective, not a checkable condition. Concrete critic completion criteria appear only in the Python example checklist. The advice to skip purely subjective critique appears only in TypeScript and Java code comments. The page does not call the sentinel check deterministic. Cited headings 'Termination conditions' and 'Recommended practices' do not exist. The max-iterations backstop is stated in prose.
- **G03** (memory, supported) Session state has four scopes selected by key prefix: unprefixed (one session), user: (shared across a user's sessions), app: (shared across the app), and temp: (lives for one invocation and is shared down a sub-agent chain). Durability depends on the service: the in-memory service persists none of it, while database-backed services persist user: and app: keys. Source: <https://adk.dev/sessions/state/>, State scopes (key prefixes); Persistence.
- **G04** (graph, supported) Agents hand off through named state keys: each step writes its output to a key and later steps read it by placeholder. Each refinement overwrites the current artifact so every check sees the latest draft, and downstream steps rely on state rather than the full conversation history. Source: <https://adk.dev/agents/workflow-agents/loop-agents/>, How state is shared.
- **G05** (graph, supported) Write state only through recorded events (output key, state delta, or callback and tool context), never by mutating a persisted session in place. Store small serializable values and identifiers, not live objects, under shallow prefixed keys. Source: <https://adk.dev/sessions/state/>, Writing state; Best practices.
- **G06** (hooks, supported) Each callback follows a return-value protocol: returning nothing continues normal flow, while returning a value short-circuits it. A before-model callback can skip the LLM call, a before-tool callback can supply a result in place of running the tool, and an after-tool callback can replace the tool output. Cross-agent security policy belongs in plugins applied at the runner, not in per-agent callbacks. Source: <https://adk.dev/callbacks/>, Callback Types table; Recommended Practices.
- **G07** (hooks, supported) A hook can deny with a reason that is returned to the agent, rewrite tool arguments before the call, or reject a response and force a retry with that reason as the next prompt. Stdout must carry only the JSON decision and logs go to stderr; exit 0 means parse the JSON, exit 2 is a system block with stderr as the reason, and other non-zero codes are only warnings. Source: <https://geminicli.com/docs/hooks/reference/>, Common stdout JSON fields; Decision and modification behavior by event (hook reference). Also Input, output, and exit codes (hooks page).
- **G08** (hooks, supported) Project-level hooks are fingerprinted: if a hook's name or command changes (for example after a pull), it is treated as new and untrusted and the user is warned before it runs. Individual hooks can be listed and enabled or disabled, and hooks run synchronously with a per-hook timeout. Source: <https://geminicli.com/docs/hooks/>, Security and trust; Managing hooks; Configuration.
- **G09** (safety, supported) Limit agent actions in layers: grant the narrowest identity permissions, expose only specific actions as tools, validate tool calls deterministically before they execute, and prefer plugins for policies that span agents. Model-generated code should run in a sandbox with no network access and cleared data between runs. Source: <https://adk.dev/safety/>, Layered defenses; Recommended practices for limiting actions.
- **G10** (evals, supported) Score both the final response and the trajectory (the sequence of tool calls). Use fast deterministic criteria, such as exact tool-call match and reference-based text match, for CI regression; use rubric-judged criteria where no reference answer exists, because LLM output varies between runs. Source: <https://adk.dev/evaluate/>, Why evaluate agents; Criteria; Recommended practices.
- **G11** (evals, supported) Tier the evals: quick unit-style test files for development, larger evalsets for slower integration runs, and recorded conformance baselines in CI that block pull requests changing expected behavior. Record efficiency metrics (tool calls, model calls, tokens, duration) across runs, reported but never used as a pass or fail. Source: <https://adk.dev/evaluate/>, Evaluation approaches; Recommended practices.
- **G12** (memory, supported) Keep session state (one conversation) separate from long-term memory (a searchable store across conversations). Memory is not saved automatically: the app calls an explicit save step, and the agent reads memory either by preloading it each turn or through an on-demand tool. Consolidate new facts with existing entries to avoid duplicates and tag entries with metadata. Source: <https://adk.dev/sessions/memory/>, Session state vs long-term memory; Storing and retrieving.
- **G13** (context, supported) Context files load hierarchically: a global file, then the workspace and its ancestors, then subdirectory files when a tool first touches that location, up to a trusted root. Split large files with imports, show the exact combined context on demand, and configure which file names the CLI reads. Source: <https://geminicli.com/docs/cli/gemini-md/>, Loading order; Imports; /memory commands; Customizing the file name.
- **G14** (harness, supported) Before an approved file-changing tool runs, the CLI snapshots project files into a shadow git repository outside the project and saves the conversation and the pending tool call. Restore reverts files and history and re-proposes the tool call. The feature is off by default, and side effects of shell commands are not documented as covered. Source: <https://geminicli.com/docs/cli/checkpointing/>, What is snapshotted; Where it's stored; Restore with /restore; What it does not cover.

### Practices

- **PR-01** (graph, supported) Save a checkpoint at the end of every execution step, after all executors in that step finish. Each checkpoint holds executor state, pending messages, pending requests and responses, and shared state, so a run can resume from any saved point rather than only the latest. Source: <https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints>, When Are Checkpoints Created?; Resuming from Checkpoints.
- **PR-02** (memory, supported) In-memory checkpoint storage loses state on restart and is for tests or demos. Production needs a persistent backend, such as a Postgres-backed saver for production and a SQLite-backed saver for local development. Source: <https://docs.langchain.com/oss/python/langgraph/persistence>, Troubleshooting common issues (MemorySaver does not persist between restarts).
- **PR-03** (loop, supported) Pause a run at a question by raising an interrupt that persists state and surfaces a JSON-serializable payload to the caller. Resume by re-invoking the same thread ID with a resume value, which becomes the return value of the interrupt call. Typed response schemas can validate the reply, and an invalid reply can be retried on the same thread. Source: <https://docs.langchain.com/oss/python/langgraph/interrupts>, Pause using interrupt; Resuming interrupts; Define an interrupt response schema.
- **PR-04** (loop, supported) On resume the node restarts from its beginning, so code before a pause runs again. Keep pre-pause side effects idempotent (for example upserts), move non-idempotent actions after the pause or into a separate node, and do not wrap the pause in a broad try/except that could swallow it. Source: <https://docs.langchain.com/oss/python/langgraph/interrupts>, Rules of interrupts (Do not wrap interrupt calls in try/except; Side effects called before interrupt must be idempotent).
- **PR-05** (loop, supported) Stop a multi-turn loop with layered conditions: a hard turn or message cap, a semantic stop such as an approval phrase, a token budget and a timeout. Conditions are checked after each agent reply, can be combined with OR (any one ends the run) or AND, and reset when a run finishes. Microsoft's group chat guide adds that a custom orchestrator must set its own round limit and termination condition, because builder-level values are ignored. Source: <https://microsoft.github.io/autogen/0.7.2/user-guide/agentchat-user-guide/tutorial/termination.html>, Termination conditions; When team stop conditions are evaluated; Combining Termination Conditions (Microsoft group chat caveat: Advanced: Custom Speaker Selection, Important note).
- **PR-06** (hooks, supported) Bound a run with a per-request cap on tool calls, counted by a hook. Calls beyond the cap are blocked even if the model keeps retrying, which guards against runaway loops. The counter resets at the start of each request. Source: <https://strandsagents.com/docs/learning/control-your-agent-with-hooks/>, Example: rate limiting tool calls.
- **PR-07** (hooks, unsupported) Put rules that must hold regardless of model reasoning into deterministic lifecycle hooks, which fire before and after invocations, model calls and tool calls. Setting a cancel value stops a tool, and the reason is returned to the model. Each sensitive tool needs its own check, because a hook only checks what it was written to check. Source: <https://strandsagents.com/docs/learning/control-your-agent-with-hooks/>, Rules that don't depend on the model; Hook architecture.
  - Verifier: As written, the claim says the hooks fire before and after model calls. The Strands page names only BeforeInvocationEvent and BeforeToolCallEvent, and a targeted re-fetch found no model-call event. Supported parts: hooks fire regardless of model reasoning, a cancel value stops the tool and returns the reason to the model, and each sensitive tool needs its own check. Narrow the claim to invocation and tool-call events.
- **PR-08** (safety, supported) Gate a destructive tool call behind human approval. The hook pauses the run until a person replies, proceeds only on an explicit yes, and cancels on any other reply, sending the cancellation message back to the model. Source: <https://strandsagents.com/docs/learning/control-your-agent-with-hooks/>, Example: human approval for deletions.
- **PR-09** (safety, supported) Enforce tool-access rules in a policy layer outside agent code. Every tool request is checked at the gateway before the tool runs, so a prompt or model mistake cannot bypass the rule. Rules can be written in Cedar or in plain language that is validated against the tool schema before use. Source: <https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html>, Introduction; Key benefits (Deterministic enforcement with strong guarantees); Key features (Policy Enforcement; Policy Authoring).
- **PR-10** (evals, supported) Shadow-test a new rule in an observe-only mode on real traffic before enforcing it. Each request is evaluated and logged, and the rule is promoted only when its decision-flip count stays at zero, meaning it would not have blocked current traffic. The engine uses default-deny and forbid-wins semantics. Source: <https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-test-a-policy.html>, How LOG_ONLY mode works; Observe LOG_ONLY results (LogOnlyDecisionFlips); Promote a policy to enforcement.
- **PR-11** (safety, supported) Write rules that depend on session history, such as requiring an approval to have happened earlier in the session, or capping how many times an action may run in one session. These temporal conditions are evaluated alongside the input-based conditions. Source: <https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html>, Introduction paragraph on session-aware temporal conditions; Key features (Temporal Policies).
- **PR-12** (other, supported) Emit traces for each agent run, model call and tool call, and correlate them with a session identifier carried in telemetry baggage. Filter sensitive content out of span attributes and payloads, and use consistent naming for services and spans from the start. Source: <https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-get-started.md>, Step 3: Enable observability for non-AgentCore-hosted agents (session.id via baggage); Best practices.
- **PR-13** (memory, supported) Prune checkpoints or set a retention policy, such as a scheduled job that deletes old checkpoints. Checkpoints accumulate over long threads and add latency and storage cost. Source: <https://docs.langchain.com/oss/python/langgraph/persistence>, Troubleshooting common issues (Checkpoints growing unboundedly).
- **PR-14** (safety, supported) Treat checkpoint storage as trusted, private infrastructure and never load checkpoints from untrusted or tampered sources. Limit which types can be deserialized with an explicit allowlist, and restrict access to the storage location. Source: <https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints>, Security Considerations (Pickle serialization; Storage location responsibility).

### Practices

- **P01** (loop, supported) Reduce the task to a clear goal and give the agent reusable tools so it can iterate. Use loops mainly where success criteria are clear and trial and error pays. Automated tests are the usual success signal, and an LLM can help build a test suite if none exists. Source: <https://simonwillison.net/2025/Sep/30/designing-agentic-loops>, Defining the goal; When to design an agentic loop; Verification and success criteria.
- **P02** (verification, supported) Start each session by having the agent run the existing test suite. This tends to make it re-run tests after its own edits and extend the suite with its own tests. Source: <https://simonwillison.net/guides/agentic-engineering-patterns/first-run-the-tests/>, Run the existing test suite first; Prompt the agent to run tests so it keeps checking its work; Put the agent in a testing mindset.
- **P03** (verification, supported) Have the agent write tests for the desired behavior, confirm they fail before any implementation, then implement until they pass. A test that already passes before implementation does not exercise the new code. Source: <https://simonwillison.net/guides/agentic-engineering-patterns/red-green-tdd/>, Write tests before implementation; Confirm the tests fail first; Implement until the tests pass.
- **P04** (safety, supported) Per-command approval prompts slow trial-and-error work. Instead, limit the files, secrets and network the agent can reach through a local container or remote sandbox, and skip permission prompts only where the environment has no internet access. The page also suggests allowlisting trusted hosts. Source: <https://simonwillison.net/2025/Sep/30/designing-agentic-loops>, The joy of YOLO mode (including its Anthropic guidance update note).
- **P05** (harness, supported) Document each tool in an AGENTS.md file with one concrete example command, which is usually enough for the agent to generalize. Prefer shell commands over MCP tools for coding agents, and run the agent where package installs cannot damage the main machine. Source: <https://simonwillison.net/2025/Sep/30/designing-agentic-loops>, Picking the right tools for the loop.
- **P06** (context, supported) A coding agent is an LLM with a system prompt and tools inside a repeating cycle, and the harness extracts tool requests and feeds results back. The model keeps no state between calls, so the harness resends the full conversation each turn, which caps tokens and raises cost. Keeping earlier content unchanged keeps cached-input pricing effective. Source: <https://simonwillison.net/guides/agentic-engineering-patterns/how-coding-agents-work/>, Core structure; The loop; Tool calls; Reading results; Context and statelessness; Context limits and cost; Caching.
- **P07** (context, supported) Delegate exploration and token-heavy work to a fresh subagent so only its summary returns to the parent. Let a test-runner subagent report only failures. Do not split work across many specialist subagents, and make each subagent reply carry everything the parent needs to continue. Source: <https://simonwillison.net/guides/agentic-engineering-patterns/subagents/>, What subagents are; When to use them; Context protection; Test running; Cautions.
- **P08** (loop, supported) Separate plan generation from execution. Validate each plan with simple rules, such as rejecting unavailable tools or overlong plans, optionally backed by an AI judge, and regenerate any plan that fails before any step runs. Write plan steps in natural language and translate them into calls as a separate step. Source: <https://huyenchip.com/2025/01/07/agents.html>, Planning.
- **P09** (loop, supported) Reflect after each step and after the full plan, and replan while the task remains unfinished. Validate plans before execution so unproductive steps do not run for hours. Reflection adds token cost and latency, and the page gives no explicit loop limit or stopping rule. Source: <https://huyenchip.com/2025/01/07/agents.html>, Loop and stopping guidance.
- **P10** (memory, supported) Split memory into working context (short-term, limited in size) and an external long-term store searched at retrieval time. Reflexion-style agents store written self-critiques of failed attempts in memory and use a simple success signal to guide the next attempt. Source: <https://lilianweng.github.io/posts/2023-06-23-agent/>, Memory Types; Planning Practices (Reflexion).
- **P11** (evals, supported) Write fast, cheap assertions for each feature and scenario that run on every change, plus generic checks that apply everywhere. Use an LLM to synthesize challenging, realistic inputs that trigger each scenario. Treat the tolerable failure rate as a product decision rather than requiring a 100 percent pass rate. Source: <https://hamel.dev/blog/posts/evals/>, Level 1: Unit Tests; Step 1: Write Scoped Tests; Step 2: Create Test Cases.
- **P12** (evals, supported) Log full conversations as traces and review them in a domain-specific viewer that puts all relevant context on one screen. Label outputs with simple good or bad judgments rather than numeric scores, and keep reading traces until they stop revealing new failure patterns. Source: <https://hamel.dev/blog/posts/evals/>, Logging Traces; Looking At Your Traces; How much data should you look at?.
- **P13** (evals, supported) Label a sample of real inputs and outputs with binary labels (pass/fail for objective criteria, win/lose/tie for comparisons) and avoid 1-5 scales. Build one evaluator per criterion, tune it until it matches held-out human labels, and run pairwise comparisons in both orders, treating inconsistent results as ties. Source: <https://eugeneyan.com/writing/product-evals/>, Step 1: Label a small dataset; Step 2: Align the LLM evaluator.
- **P14** (safety, supported) Layer guardrails on outputs and inputs: constrain generation with structured-output tooling, run syntactic checks (allowed values, numeric ranges, valid SQL or code), screen content with moderation, check semantic consistency with the source material, and filter inputs before the model answers. Source: <https://eugeneyan.com/writing/llm-patterns/>, Guardrails.

### Practices

- **huntley-fresh-context-one-task** (loop, supported) Run the agent in a shell loop where each iteration does one task in a fresh context, reloads the same plan and spec files, and keeps progress in files and git instead of model memory. Source: <https://ghuntley.com/ralph/>, Iteration execution; State between iterations.

- **huntley-no-placeholders** (verification, supported) Tell the agent explicitly not to write placeholder or minimal implementations, since models tend toward them, and move any leftovers onto the to-do list. Source: <https://ghuntley.com/ralph/>, Verification and backpressure (no cheating).
- **huntley-operating-guide-prune** (memory, supported) Keep a short agent-facing guide on how to build and run the project that the agent updates as it learns, log unrelated bugs in the plan file, and prune completed items from the plan so it stays manageable. - **bockeler-context-small-on-demand** (context, supported) Keep always-loaded context small: put path-scoped guidance in rules, task instructions and scripts in skills loaded only when needed, delegate large work to subagents with their own context window, and use lifecycle hooks for steps that must happen every time instead of relying on the model to remember them.
