# v0.0.24 — Release hygiene and the version scheme

The owner set a versioning scheme for the Inonu Harness and asked that it be a global concept of the Harness, for every project it manages ([decisions.md](decisions.md) D4): a project starts at v0.0.1 and each milestone raises the patch number, with at most two digits for the minor and the patch, so that v0.1.0 comes after v0.0.99 and v1.0.0 only after a long evolution. This milestone carries the scheme (R8 to R13) together with the release-hygiene checks below. Every earlier version of this repository was renumbered from v0.N.0 to v0.0.N in the same change, so this is the 24th milestone and is v0.0.24.

A research round ([gaps](research-gaps.md)) found two small gaps that no check covers. The version of the package is written in three manifests and six test assertions, and nothing compares the manifests; a `SKILL.md` has no size limit, while superpowers fails a skill of 20,000 bytes or more and the Claude Code documentation advises under 500 lines. The scope was chosen by the Jev judge from [brief.md](brief.md) ([decisions.md](decisions.md)).

## Requirements

- R1 A new module `inonu_harness/versions.py` with `audit(root: Path) -> list[str]`, which returns one fixed-form problem line per inconsistency and an empty list when everything agrees, and a `main` so that `python -m inonu_harness.versions [--root DIR]` (default: the current directory) prints each problem on stderr and exits 1, or exits 0 when there is none. It reads files only and writes nothing.
- R2 It compares these versions, read without importing the package: `__version__` in `inonu_harness/__init__.py` (a line `__version__ = "…"`), `version` under `[project]` in `pyproject.toml`, and `version` in `.claude-plugin/plugin.json`. If `.claude-plugin/marketplace.json` has a `version` at the top level or in an entry of `plugins`, that is compared too. A manifest that does not exist is skipped, so a root with none of them passes. A manifest that exists but cannot be parsed, or has no version, is a problem. Two different versions are a problem that names both files and both versions.
- R3 `check` (and `check --ref`) runs the audit as a new step named `versions`, after `compile` and before `tests`, as a subprocess in the checked directory like the other steps. The report format and the other steps are unchanged.
- R4 The six hard-coded version assertions in `tests/test_check_bundle.py` (2) and `tests/test_host_profiles.py` (4) compare against `inonu_harness.__version__`, or against the manifest they test, instead of a literal string. A release then needs the three manifest edits only.
- R5 `docs lint` also reads every `SKILL.md` below `skills/` of the root (directory links handled as for `docs/`). A `SKILL.md` of 20,000 bytes or more gets the finding `skill_file_too_large`, and one of 500 lines or more gets `skill_file_too_long`, each with a fix hint. The limits are the constants `SKILL_MAX_BYTES` and `SKILL_MAX_LINES`; the `max_bytes` and `max_lines` arguments keep applying to the instruction files only. Links in a `SKILL.md` are checked like links in docs, relative to its own directory. The existing skill must pass without being edited.
- R6 Tests cover:
  - the audit: all three agree; each one differing in turn; one missing; none present; a manifest that is malformed or has no version; `__init__.py` without a `__version__` line; the marketplace `version` compared when present; the exit codes and stderr of `main`; nothing written;
  - `check`: the `versions` step appears in order and is present for `--ref`; a mismatch in a temporary root fails the check; a root without manifests still passes;
  - the lint: a skill at 19,999 and at 20,000 bytes, at 499 and at 500 lines; a skill nested one level down; a skill in a linked directory outside the root is not read; a broken link in a skill is reported; a skill under `docs/` is not treated as a skill.
- R7 Docs: CHANGELOG 0.0.24, README, a short note in the docs that a release edits three manifests, and a skill bullet. Version 0.0.24 in the three manifests.

- R8 The scheme, in `inonu_harness/versions.py`: a version is `0.MINOR.PATCH` where MINOR and PATCH are integers from 0 to 99 written without leading zeros, and the version is not `0.0.0`. Milestone number n is the version `0.(n // 100).(n % 100)`: milestone 1 is `0.0.1`, milestone 99 is `0.0.99`, milestone 100 is `0.1.0`, milestone 199 is `0.1.99`. A function `in_scheme(version)` says whether a text is such a version. A function `next_version(version)` returns the next milestone's version: `0.0.24` gives `0.0.25`, `0.0.99` gives `0.1.0`, `0.1.99` gives `0.2.0`; for a text outside the scheme, and for `0.99.99`, which is the last version of the scheme, it raises `ValueError` with a fixed message (version 1.0.0 is declared by the owner, never computed).
- R9 `audit(root, scheme=False)` and `python -m inonu_harness.versions [--root DIR] [--scheme] [--next]`: with `scheme` (`--scheme`) every stated version must also be in the scheme, and a version that is not gets a problem line naming the file and the version. With `--next` the command prints the next milestone's version computed from the agreed version on stdout and exits 0, or exits 1 with the problem lines when the manifests disagree, have no version, or the version is outside the scheme. The default audit keeps R1 and R2 unchanged, so a project that has not adopted the scheme still gets the consistency check.
- R10 `python -m inonu_harness version [--root DIR] [--scheme] [--next]` (and so `scripts/inonu.py version ...`, which the installed skill uses) runs the same code and returns the same exit codes. The `versions` step of `check` runs with `--scheme`, so this repository cannot leave the scheme.
- R11 The concept is written for every project, in [docs/versioning.md](../../../versioning.md): the scheme, the mapping between a milestone and a version, the milestone directory name `docs/specs/milestones/vMAJOR.MINOR.PATCH`, that all manifests carry the current milestone's version, that 1.0.0 is the owner's decision, how an existing project that does not start at 0.0.1 adopts it (the next milestone is the next free version in the scheme, never a lower one) and the table that maps the old numbers of this repository (v0.N.0 for N from 1 to 24) to the new ones. `AGENTS.md` points to it, and the skill states the rule and the commands in its description and a bullet, so that the profile installed for Claude and Codex carries it to every project.
- R12 Tests cover the scheme (valid and invalid forms, including `0.0.0`, `0.01.1`, `0.0.100`, `1.0.0`, `v0.0.1`, a pre-release suffix and whitespace), `next_version` at every boundary, `audit` with and without `scheme`, `main` and the `version` subcommand with their exit codes and output, the `versions` step of `check` passing `--scheme`, and a test that the manifests of this repository are in the scheme.
- R13 The review of the first implementation (R1 to R7) found problems that the tests must now cover: a `__version__` line inside a docstring or comment, a version line with a trailing comment, single quotes or an annotation, an unreadable or oversized manifest and a directory where a manifest belongs (a problem line, never a crash), a byte order mark, deeply nested or duplicate-key JSON, a skill measured in bytes and not characters (a file of 10,000 two-byte characters is 20,000 bytes), a skill file name in another case, a folder under `skills/` that cannot be listed (`directory_unreadable`, fail closed), a `skills/` folder that is a link inside the root (walked at its real place) or outside it (`link_escapes_root`), and the symbolic-link case for a `SKILL.md`.

## Out of scope

Protecting check files in the loop runner (gap C), token formats in the Jev adapter (gap D), a CI workflow change, a script that rewrites manifests (the command only reports the next version), per-language manifests other than the three above, and rewriting version numbers that appear in the git history.
