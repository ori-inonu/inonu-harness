# v0.0.24 research: star-ranked harness, loop and graph repositories

Date: 2026-10-26. The repositories were taken from the GitHub search API ordered by stars, for the queries 'agent harness', 'agentic loop', 'claude code harness', 'context engineering agents' and 'spec driven development', keeping the ones that are real harness, loop or skill frameworks and that earlier research had not covered (ECC, spec-kit, Beads, Graphiti and similar were covered in 0.0.10 and 0.0.20). Star counts are the ones the readers recorded and the verifiers re-read on the same day.

Method: one reader per repository pinned HEAD to a commit SHA, read only through `gh api` GET calls (no clone, no download, nothing run), and cited each mechanism as a path and line range. An independent verifier re-fetched the cited files at that SHA. Every reader and verifier was a Haiku-class model and no human read the code, so 'supported' means a second model found the file showing it. The readers compared each mechanism with a short description of Inonu, not with its code; the corrections below show where that description was too thin. The gaps that survive a check against Inonu's own code are in [research-gaps.md](research-gaps.md).

### Mechanisms

- **M01** (hooks, supported) SessionStart bootstrap injection: One SessionStart hook, matched on startup, clear and compact, runs a shell script that reads the using-superpowers SKILL.md and emits it as additional context inside an override wrapper. The script always exits 0, so it never blocks a session. SessionStart is the only hook event the repo declares, so nothing gates tool use or stop. Evidence: `hooks/hooks.json` 3-15; `hooks/session-start` 18-25, 40-41, 85.
- **M02** (hooks, supported) Polyglot hook dispatcher with per-host JSON envelopes: run-hook.cmd is one file that is both a Windows batch file and a bash script. On Windows it locates Git Bash (standard install paths, a per-user path, then PATH) and exits 0 silently if none is found. On Unix it execs the named extensionless script with the running bash. The session-start script picks the JSON envelope from environment variables hosts set (Cursor, Claude Code, Muse, Copilot CLI), and the hook config forces the bash shell. Evidence: `hooks/run-hook.cmd` 1-9, 18-41, 46-47, 56-62; `hooks/session-start` 43-50, 71-83; `hooks/hooks.json` 9-11; `docs/windows/polyglot-hooks.md` 29-31.
- **M03** (memory, supported) Per-plan git-ignored workspace with ownership marker: sdd-workspace maps a plan file to a per-plan directory under .superpowers/sdd/ inside the working tree, not under .git, which the host protects. A plan-path marker records which plan owns the directory. If another plan already owns the slug, it retries with the parent directory name and then a counter. A create-only, self-ignoring .gitignore keeps every workspace out of git status. Evidence: `skills/subagent-driven-development/scripts/sdd-workspace` 6-9, 21-25, 56-82, 84-86.
- **M04** (memory, supported) Ledger as recovery map with resume rule: Each plan has a progress.md ledger whose first line names the plan. The controller creates it before dispatch and appends one completion line per task. After compaction the controller trusts the ledger and git log over its own memory. A resuming controller skips every task with a complete line, resumes a mid-loop task at its next round, and leaves another plan's ledger untouched. Evidence: `skills/subagent-driven-development/SKILL.md` 108-127; `skills/subagent-driven-development/references/resuming.md` 6-12.
- **M05** (verification, supported) Task-completion gate that records only on exit 0: task-done runs one test command, saves its full log in the workspace, prints the tail, and appends a task-complete line (commit range plus last output line) only if the command exits 0. A non-zero exit records nothing and returns the same status code. The ledger line renders the command so the record shows exactly what was run. Evidence: `skills/executing-plans/scripts/task-done` 25-26, 39-51.
- **M06** (loop, supported) Deterministic review package and fence-aware task brief: review-package checks that BASE is an ancestor of HEAD and that the range is non-empty (exit 3 otherwise), then writes the commit list, a stat summary and a diff with 10 lines of context into one file for the reviewer. task-brief awk-extracts a single plan task section, skipping lines inside code fences, and exits 3 when no heading matches. Both keep plan text and diffs out of the controller's context. Evidence: `skills/subagent-driven-development/scripts/review-package` 22-28, 39-50; `skills/subagent-driven-development/scripts/task-brief` 30-41; `skills/subagent-driven-development/SKILL.md` 182-184, 199-213, 259-267.
- **M07** (loop, supported) Fresh implementer per task with a separate two-verdict reviewer: The controller dispatches a fresh implementer per task with a brief file, a report file and a recorded BASE commit. Implementers must not spawn subagents, including reviewers. After a DONE report, a separate reviewer reads the review package and returns two verdicts, spec compliance and code quality; a report missing either verdict is not accepted. Non-DONE statuses (DONE_WITH_CONCERNS, NEEDS_CONTEXT, BLOCKED) route to a separate reference. Evidence: `skills/subagent-driven-development/SKILL.md` 8-12, 197-201, 223-228, 237-257; `skills/subagent-driven-development/implementer-prompt.md` 50-60, 80-90; `skills/subagent-driven-development/task-reviewer-prompt.md` 3-5, 52-58.
- **M08** (loop, supported) Bounded fix loop with escalation and a breaker: Each task gets at most five fix rounds. Rounds 1-3 resume the same implementer; rounds 4-5 hand the task to a fresh, more capable implementer. Every round ends with a scoped re-review of the fix diff only and one ledger line. Minor findings are logged and never enter the loop. After round 5 the controller adjudicates each open finding: park it with a ruling, or rule on load-bearing ones and ledger the change. Evidence: `skills/subagent-driven-development/references/fix-loop.md` 7-19, 20-35, 44-54, 59-77; `skills/subagent-driven-development/SKILL.md` 156-157, 294-302.
- **M09** (harness, supported) Rulings-not-stalls autonomy policy with a ruling log: A running plan does not wait on the human for conflicts or ambiguities. The controller records each decision as a ledger ruling with three parts (what was decided, why, and what it costs if wrong) and continues. Only four events stop the run: an irreversible or destructive operation, a security-sensitive action, a side effect outside the worktree (merge, push to a shared branch, publish), and a plan so broken that every path is a guess. The final message lists every ruling. Evidence: `skills/subagent-driven-development/SKILL.md` 17-31; `skills/subagent-driven-development/references/final-review.md` 33-40; `skills/subagent-driven-development/references/preflight.md` 20-25.
- **M10** (verification, supported) Completion-claim iron law (prompt-level gate): A skill forbids completion claims without fresh output from the verification command in the same message. It sets a gate (identify the command, run it fully, read exit code and failure count, then claim), maps each claim type to its required evidence, lists red-flag phrases, and says to check the VCS diff instead of trusting an agent's success report. It is enforced by prose, not by a tool. Evidence: `skills/verification-before-completion/SKILL.md` 14-36, 40-48, 50-59, 100-104.
- **M11** (skills, supported) Hard gate between design approval and planning: The brainstorming skill wraps the rule in a HARD-GATE block: nothing is built until the human approves the written design doc, and the only allowed next skill is the planning skill. Before that, the agent must lay out approaches in its own message and get a pick. The gate is prose-enforced, not a tool check. Evidence: `skills/brainstorming/SKILL.md` 26-32, 247-261.
- **M12** (skills, supported) Plan contract with required header, Global Constraints and Review Focus: writing-plans requires a fixed header with a REQUIRED SUB-SKILL pointer to the execution skill and a Spec line, a Global Constraints section copied verbatim from the spec, and a Review Focus section listing input classes the spec implies. It also requires a file-structure map before tasks and checkbox steps where each step is one checkable action. Evidence: `skills/writing-plans/SKILL.md` 23-32, 43-50, 52-87.
- **M13** (verification, supported) Skill authoring as TDD with a skill size budget: writing-skills maps RED-GREEN-REFACTOR onto pressure scenarios run with subagents (baseline before the skill is written) and tells authors to automate mechanical constraints instead of documenting them. tests/skill-size fails any SKILL.md at or above 20,000 bytes, because Claude Code re-attaches skills truncated at that size after compaction. Behavior evals live in an external eval lab that runs real LLM sessions; only static gates are meant for public CI. Evidence: `skills/writing-skills/SKILL.md` 10-18, 30-45, 59; `tests/skill-size/test-skill-size.sh` 2-8, 16, 19-30; `docs/testing.md` 25-37; `AGENTS.md` 99-106.

### Mechanisms

- **M01** (loop, supported) Bounded agent turn loop with steer and interrupt: A ConversationRuntime streams a model response, collects tool_use blocks, runs each through hooks and the permission check, executes it, runs post hooks, and feeds results back. The loop ends when the response has no tool calls, when an interrupt or abort is seen, or with an error when an iteration cap is exceeded. Queued steer text is appended before the loop continues. An interrupted turn gives every pending tool call a synthetic error result so the session stays valid. The default cap is effectively unbounded unless with_max_iterations is set. Evidence: `rust/crates/runtime/src/conversation.rs` 573-621; `rust/crates/runtime/src/conversation.rs` 354; `rust/crates/runtime/src/conversation.rs` 131-208; `rust/crates/runtime/src/conversation.rs` 682-723; `rust/crates/runtime/src/conversation.rs` 844-858.
- **M02** (hooks, supported) Shell hook protocol with exit-code semantics and fail-closed pre-hook: Hook commands are configured per event (PreToolUse, PostToolUse, PostToolUseFailure) and filtered by tool name. Each command receives the event JSON on stdin and HOOK_* environment variables. Exit 0 allows, with stdout JSON able to set deny, updated input or a permission override. Exit 2 denies. Any other exit is a failure. A failed or cancelled pre-hook denies the tool. Commands run in order and the first deny or failure stops the chain. A post-hook failure marks the tool result as an error. The runtime has no Stop-style end-of-turn event. Evidence: `rust/crates/runtime/src/hooks.rs` 22-26; `rust/crates/runtime/src/hooks.rs` 342-418; `rust/crates/runtime/src/hooks.rs` 421-441; `rust/crates/runtime/src/hooks.rs` 449-470; `rust/crates/runtime/src/conversation.rs` 724-768; `rust/crates/runtime/src/conversation.rs` 793-819; `rust/crates/plugins/src/hooks.rs` 11-14; `rust/crates/plugins/src/hooks.rs` 191-196.
- **M03** (hooks, supported) Hook trust layering: project-scoped hooks are dropped: Config is read from a fixed list of files: user-level legacy and settings files, project .claw.json and .claw/settings.json, and a local settings.local.json. If a project-scoped file contains a hooks key, that key is removed and a warning is emitted, because there is no trust approval flow for project hooks yet. Hook entries are parsed only for the three known event names. Evidence: `rust/crates/runtime/src/config.rs` 442-469; `rust/crates/runtime/src/config.rs` 684-699; `rust/crates/runtime/src/config.rs` 1771-1835.
- **M04** (memory, supported) Layered instruction discovery with budgets, plus memory index framed as context: Instruction files are discovered from candidate directories derived from the working directory. Names include CLAUDE.md, AGENTS.md, CLAUDE.local.md, and .claw or .claude variants. Duplicates are removed by normalized content. Rendering enforces a per-file character cap and a total cap, and a git diff section has its own cap. The memory section injects the MEMORY.md index, capped at 200 lines, and tells the model that this content came from a prior session and is context, not instructions. Evidence: `rust/crates/runtime/src/prompt.rs` 40-43; `rust/crates/runtime/src/prompt.rs` 327-369; `rust/crates/runtime/src/prompt.rs` 575-612; `rust/crates/runtime/src/prompt.rs` 257-290; `rust/crates/runtime/src/memory_store.rs` 1-7; `rust/crates/runtime/src/memory_store.rs` 16-30; `rust/crates/runtime/src/memory_store.rs` 84-101; `rust/crates/runtime/src/memory_store.rs` 126-131.
- **M05** (graph, supported) Session JSONL store with rotation, atomic writes, redaction and fork: Each save renders a full JSONL snapshot, rotates the existing file once it passes 256 KiB while keeping at most 3 rotated files, writes atomically, and cleans up old rotations. Incremental message appends also exist. Known secret markers such as API key prefixes are redacted, and any persisted field over 16 KiB is truncated before writing. Sessions can be forked to branch a conversation. Evidence: `rust/crates/runtime/src/session.rs` 14-16; `rust/crates/runtime/src/session.rs` 231-261; `rust/crates/runtime/src/session.rs` 339; `rust/crates/runtime/src/session.rs` 628-659; `rust/crates/runtime/src/session.rs` 1138-1170; `rust/crates/runtime/src/session.rs` 1340.
- **M06** (harness, supported) Ordered permission gate with deny-first precedence: Five modes exist: read-only, workspace-write, danger-full-access, prompt and allow. authorize_with_context checks in order: a denied-tools list, deny rules, the hook override (deny, ask or allow), ask rules, and then allow rules and the mode ladder. A hook allow is an override that does not skip ask rules or the mode ladder. A separate enforcer adds file-write and bash checks before dispatch. Evidence: `rust/crates/runtime/src/permissions.rs` 12-17; `rust/crates/runtime/src/permissions.rs` 236-300; `rust/crates/runtime/src/permission_enforcer.rs` 14; `rust/crates/runtime/src/permission_enforcer.rs` 39; `rust/crates/runtime/src/permission_enforcer.rs` 110; `rust/crates/runtime/src/permission_enforcer.rs` 147.
- **M07** (harness, supported) Scoped, single-executor approval grants with expiry and audit: A grant starts pending, then becomes granted. It is bound to a policy scope (policy, action, optional repository and branch), to an approving actor, and to one approved executor, with optional expiry and max uses. verify() checks without consuming. consume() increments uses and marks the grant consumed at the cap. Checks cover status, expiry, uses, exact scope match and executor match. Delegation hops are recorded in an audit trail. The ledger is in memory and has replay protection.
