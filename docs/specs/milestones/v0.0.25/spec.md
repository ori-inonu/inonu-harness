# v0.0.25 — Milestone management: `milestone new` and `milestone check`

The owner asked that version and milestone management be a global concept of the Inonu Harness, for every project, and for a reverse engineering of GSD (Get Shit Done), whose milestone flow is documented in [research-synthesis.md](research-synthesis.md). GSD keeps the milestone's requirements, audit and numbering in model prose; this milestone moves the mechanical part into code: a scaffold that numbers the next milestone with the scheme of [docs/versioning.md](../../../versioning.md), and a check that proves requirement coverage and structure from the Markdown a milestone already has. The scope was chosen by the Jev judge from [brief.md](brief.md) ([decisions.md](decisions.md)).

## Requirements

- R1 A new module `inonu_harness/milestones.py` with `new_milestone(root, directory, title=None)` and `check_milestones(root, directory, versions=(), start=None)`, and a `main` so that `python -m inonu_harness.milestones new|check ...` works. It imports only `inonu_harness.versions` from the package, so that a checkout with just these two modules can run it. `python -m inonu_harness milestone new|check ...` (and so `scripts/inonu.py milestone ...`) runs the same code with the same exit codes. Both take `--root DIR` (default: the current directory) and `--dir RELDIR` (default `docs/specs/milestones`, a relative path below the root).
- R2 Containment: the milestones directory must resolve inside the root. A root that does not exist is exit 2. A milestones directory that does not exist means no milestones: `check` passes with nothing to check, and `new` creates it. A milestones directory, or any parent of it below the root, that is a link resolving outside the root is refused with exit 2. Only files below the root are read or written, and no output line contains an absolute path.
- R3 `milestone new [--title TEXT]` creates the folder of the next milestone with `spec.md`, `decisions.md` and `tasks.md` from fixed templates and prints one JSON object: `{"schema_version": 1, "version": "0.0.N", "directory": "<relative path>", "files": [...]}`. No other file is created: `checkpoint.md` belongs to the close of a milestone.
- R4 The next version is computed, never typed: if the manifests of the root state a version in the scheme (the three manifests read by `inonu_harness.versions`), it is `next_version` of that version; otherwise, if in-scheme milestone folders exist, it is `next_version` of the highest one; otherwise it is `0.0.1`. When the manifests state a version that is not in the scheme or disagree with each other, `new` exits 1 and creates nothing. When the computed folder already exists (as a directory or any other entry), `new` exits 1 and changes nothing; when the scheme is at its last version (`0.99.99`), `new` exits 1 with the same fixed message as `version --next`.
- R5 Safety of `new`: files are created exclusively (never overwriting), the folder is created only after the checks above pass, and if any file cannot be written the files and the folder created by this run are removed before exit 1. `--title` is a single line of 1 to 120 characters without control characters, else exit 2; it appears only in the headings of the templates.
- R6 The templates are fixed English text with angle-bracket placeholders. `spec.md` has the heading `# v0.0.N — <title>`, a `## Requirements` section with the line `- R1 <...>` and an `## Out of scope` section. `tasks.md` has a table with the columns `Task`, `Depends on`, `Ownership` and `Acceptance` and one row `T01` whose acceptance cites `R1`. `decisions.md` has `## D1 — Scope`. A folder just created by `new` must pass `check`.
- R7 `milestone check [VERSION ...] [--from VERSION]` reads the milestone folders under the directory (all, or only the named versions, or those from `--from` on, in version order) and prints one JSON object: `{"schema_version": 1, "status": "pass" or "fail", "milestones": [{"version", "findings": [...]}]}` with findings sorted by version, severity, rule and line. Exit 0 when there is no finding of severity `error`, 1 otherwise, 2 for invalid input (a missing root, a bad `--dir`, a version argument that is not in the scheme).
- R8 Folder rules: a directory whose name does not match `v<digits>.<digits>.<digits>` is `milestone_name_invalid` (error); one that matches but is not in the scheme (including `v0.0.0`, `v0.01.1`, `v0.0.100` and `v1.0.0`) is `milestone_not_in_scheme` (error). Files that are not directories are ignored. `spec.md` or `tasks.md` missing is `required_file_missing` (error); `decisions.md` missing is `decisions_missing` (warning). A file that cannot be read, is not a regular file, is not UTF-8 or is larger than 1 MiB is `file_unreadable` (error); a milestone folder or file that resolves outside the root is `link_escapes_root` (error) and is not read.
- R9 Requirement rules, applied to a milestone whose `spec.md` defines requirements: a requirement is a top-level list item (`-` or `*`, optionally bold) that starts with `R<n>` (at most 9 digits), outside fenced code blocks and HTML comments, under `## Requirements` or under any later heading that starts with `Revision`, until a heading for deferred work (`Out of scope`, `Non-goals`, `Not in scope` or `Deferred`). The same id twice is `requirement_duplicate` (error); ids that do not run 1..n without a gap are `requirement_gap` (warning). A `spec.md` with no such item gets `requirements_not_found` (warning) and no coverage rules.
- R10 Coverage rules: references are read from the table rows (lines starting with `|`) of `tasks.md`, outside fenced code blocks: `R<n>` and the ranges `R<a>–R<b>`, `R<a>-R<b>` and `R<a>..R<b>` (the end may omit the `R`). A defined requirement that no row cites is `requirement_unclaimed` (error), reported with its id. A cited id that the spec does not define is `task_cites_unknown_requirement` (error). A range whose end is before its start, or that covers more than 1000 ids, or an id with more than 9 digits, is `reference_range_invalid` (error). A citation glued to letters, digits or an underscore (`R2D2`) is not a citation. More than 10,000 references in one `tasks.md` is `reference_limit_exceeded` (error) and no coverage rule runs; more than 50 findings of one coverage rule are cut to 50 with one `findings_truncated` (error). A `tasks.md` with no table row gets `tasks_not_found` (warning) and no coverage rules.
- R11 `check` of this repository: `check` (and `check --ref`) runs a step `milestones`, as `python -m inonu_harness milestone check --from 0.0.9`, only when `docs/specs/milestones` exists in the checked directory (or a symbolic link is committed under it), after `versions` and before `tests`. With `--ref`, a symbolic link committed under the milestones folder fails the step, because the export writes it as a plain file. The milestones before v0.0.9 predate the `R<n>` format and are not checked. All 16 milestones from v0.0.9 on pass today; a test pins that.
- R12 Tests cover:
  - the scaffold: the first milestone `0.0.1` in an empty root, the next version from manifests, from the highest folder and from both, a manifest outside the scheme or in disagreement, an existing folder or file in the way, `0.99.99`, the `--title` limits, a failed write that rolls back, exclusive creation, no absolute path in the output, and that the result passes `check`;
  - containment: a milestones directory that is a link out of the root (a junction fallback where links need a privilege), a `--dir` that escapes with `..` or is absolute;
  - the check: each rule of R8 to R10 with its boundary (a range at 1000 and 1001, `R1–R5`, `R1-R5`, `R1..R5`, `R3–R1`), a requirement inside a fenced block, ids with a gap, duplicates, a spec in the legacy format, a table cell with the same id twice, bold ids, an unreadable or oversized file, `--from` and named versions, sorted findings, and exit codes;
  - the `check` step: present with the milestones directory, absent without it, failing on a milestone with an unclaimed requirement, also for `--ref`;
  - the repository itself: `check_milestones` on this repository with `start="0.0.9"` has no error.
- R13 Docs: a new `docs/milestones.md` for any project (the folder, the files, what each rule means, the commands, how a milestone closes and the manifests are bumped, and the GSD comparison in one short section); links from `README.md` and `AGENTS.md`; CHANGELOG 0.0.25; a Portuguese paragraph in `docs/sdd-workflow.md`; a bullet in the skill with both commands, so that the installed profile carries them to every project. Version 0.0.25 in the three manifests.

## Out of scope

Closing a milestone (the deferred-items ledger and a `MILESTONES.md` index), append-only gap tasks, pause and resume, parsing the older formats, writing `checkpoint.md`, bumping the manifests, git tags, and any change to `sdd audit`.
