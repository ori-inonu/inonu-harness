## Summary

GSD 2 (gsd-build/gsd-2, MIT, pinned to 33c00aaf) is a TypeScript orchestrator for AI coding agents, with its own pi-* packages. Runtime state is DB-authoritative: .gsd/gsd.db (node:sqlite or better-sqlite3) holds milestones (M###), slices (S##) and tasks (T##) as rows, and markdown files are rendered projections. A kernel of pure decision functions and an ordered dispatch rule table choose each unit. Each unit runs in a new agent session under soft, idle and hard timeouts. Stuck detection, retry, cooldown and budget checks live in code. Milestones run on milestone/<MID> worktrees and squash-merge to main. The repository is archived and points to open-gsd/gsd-pi. Static reading only.

- **F03** (numbering, seen, supported) **Milestone IDs are M plus three digits with an optional six-character suffix.** The anchored regex accepts M### or M###-[a-z0-9]{6}. - **F09** (verification, seen, supported) **Stuck detection is a sliding-window function with four rules.** Rule 1: the same error twice in a row. Rule 2: the same unit key three times in a row. Rule 2b: the same key three times anywhere in the window. Rule 3: an A-B-A-B oscillation in the last four entries. Rule 4: the same ENOENT path in two entries. Rules 2 and 2b are suppressed while unit_dispatches shows a retry still inside backoff (attempt below max and next_run_at in the future). The reason string carries a logger summary. The orchestrator uses a six-entry window. Evidence: `src/resources/extensions/gsd/auto/detect-stuck.ts` 31-43, 45-138; `src/resources/extensions/gsd/auto/orchestrator.ts` 11-19.
- **F10** (state, seen, supported) **Hard loop bounds and failure counters are constants, not preferences.** MAX_LOOP_ITERATIONS is 500 and stops the loop with a max-iterations reason. Memory pressure is checked every 5 iterations and stops gracefully. Custom-engine verify retries are capped at 3. Cooldown retries are capped at 5, with a fallback wait of 35 s, or the provider retry-after value plus 500 ms when it is 60 s or less. - **F11** (state, seen, supported) **Three timeout tiers per unit: soft wrap-up, idle watchdog, hard pause.** The soft timeout posts a wrap-up warning and triggers a turn only when no tool is in flight. The idle watchdog polls on an interval. It treats an in-flight tool older than the idle window as hung, except tools waiting on human input, and it skips the idle verdict when the working tree has changes. The hard timeout runs recovery and pauses auto-mode. A per-task estimate scales the soft and hard windows, capped at 6x. Project-research units are capped at 3 minutes soft and 5 minutes hard. The runUnit failsafe uses hard 30 minutes and idle 10 minutes defaults plus a buffer, and a 120 s session-creation timeout. ## Lifecycle

1. **1. Derive state** — deriveState in state.ts. Inputs: .gsd/gsd.db and optional projectRootForReads. Outputs: GSDState with phase, active milestone, slice and task, blockers and recent decisions. Gate: DB must be open; if not, return pre-planning with a blocker and no markdown inference unless the env flag is set.
2. **2. Plan or discuss a milestone** — agent unit (discuss-milestone, plan-milestone) calling gsd_plan_milestone, gsd_plan_slice and gsd_plan_task. Inputs: user answers, research, prior decisions, requirement rows. Outputs: milestone, slice and task DB rows; ROADMAP and PLAN projections rendered from the DB. Gate: write-gate milestone depth check (inferred); the plan-gate rules are prompt-level.
3. **3. Advance the orchestrator** — AutoOrchestrator.advance in orchestrator.ts. Inputs: lock state, resource version, health snapshot, reconciled state. Outputs: blocked result with pause, or continue to dispatch; each gate emits a UOK gate record and a journal entry. Gate: ensureLockOwnership, resource-version guard, pre-dispatch health gate, reconcileBeforeDispatch; any failure blocks.
4. **4. Choose the next unit** — DISPATCH_RULES in auto-dispatch.ts, first match wins. Inputs: GSDState (phase, active slice and task), preferences, session context. Outputs: dispatch action with unitType, unitId and a prompt built from DB content, or a stop with reason and level. Gate: stop rules (escalation pending, missing slice, complete) and a fall-through to an explicit stop.
5. **5. Claim the unit** — recordDispatchClaim in db/unit-dispatches.ts and milestone lease claim in db/milestone-leases.ts. Inputs: unit key, worker ID, lease token, attempt and max attempts. Outputs: unit_dispatches row with status claimed. Gate: partial unique index on active claims; skip on already-active or stale-lease (workflow-kernel decideDispatchClaim).
6. **6. Run the unit in a new session** — runUnit in auto/run-unit.ts with pi.sendMessage (customType gsd-auto, triggerTurn). Inputs: prompt text, model, provider readiness. Outputs: agent_end result, or cancelled with an error context. Gate: session creation within 120 s; provider readiness; agent_end or the failsafe timeout; supervision timers run alongside.
7. **7. Agent writes state through tools** — gsd_* tools registered in bootstrap/db-tools.ts (for example gsd_task_complete). Inputs: tool arguments validated against schema. Outputs: DB rows updated; markdown summaries and checkboxes rendered from the DB. Gate: tool schema validation; write gate for milestone CONTEXT files.
8. **8. Post-unit verification** — runPostUnitVerification in auto-verification.ts (execute-task and validate-milestone only). Inputs: unit type, verification evidence, retry count. Outputs: continue, retry (pendingVerificationRetry set) or pause. Gate: verification_evidence rows; retries exhausted leads to pause.
9. **9. Finalize and guard** — decideFinalizeResult, detectStuck over the window, decideIterationErrorRecovery in workflow-kernel and detect-stuck. Inputs: finalize input, window of unit keys and errors, consecutive error count. Outputs: complete, retry or stop with a failure class; stuck verdict with reason. Gate: stuck rules, three consecutive iteration errors, MAX_FINALIZE_TIMEOUTS, MAX_LOOP_ITERATIONS.
10. **10. Slice and milestone progression** — DISPATCH_RULES: summarizing to complete-slice, run-uat, uat-verdict-gate, reassess-roadmap, validating-milestone to validate-milestone, completing-milestone to complete-milestone. Inputs: slice and milestone rows, UAT verdict, validation terminal state. Outputs: completed slice and milestone rows; reassessment artifacts. Gate: UAT verdict must be PASS to progress; validation terminal state required.
11. **11. Merge the milestone branch** — mergeMilestoneToMain in auto-worktree.ts (called through the worktree lifecycle module). Inputs: milestone/<MID> branch and integration branch. Outputs: one squash commit on main, branch deleted, worktree removed. Gate: MergeConflictError on conflict; nothing-to-commit is safe only if the work is already on the integration branch.
12. **12. Complete** — complete to stop rule in auto-dispatch.ts; decideEngineReconcile returns complete-workflow. Inputs: milestone status from DB. Outputs: Workflow complete stop reason. Gate: milestone status must be closed.
13. **13. Recover after a crash** — crash-recovery.ts readCrashLock, findStaleAutoWorker and emitCrashRecoveredUnitEnd. Inputs: workers heartbeat, PID liveness, unit_dispatches row, runtime_kv session file. Outputs: synthetic unit-end with reason crash-recovered; stale worker marked canceled. Gate: heartbeat past TTL and PID not alive.

## Numbering rules

- Milestone ID: the letter M followed by exactly three digits, with an optional hyphen and six characters from a-z0-9 in unique mode. The anchored regex in milestone-ids.ts rejects anything else.
- Next milestone ID: the maximum existing numeric part plus one, zero-padded to three digits. Reserved preview IDs count as existing. Inferred consequences: deleting the highest milestone frees its number, and a 1000th milestone would fail the three-digit regex.
- Milestone discovery reads directory names that start with M and digits, then orders them by custom queue order, falling back to numeric order.
- Slice ID: S followed by two digits by convention (S01). The DB keys slices by (milestone_id, id) and orders them with a sequence column. No enforcing regex was found in the files read.
- Task ID: T followed by two digits by convention (T01). The DB keys tasks by (milestone_id, slice_id, id). No enforcing regex was found in the files read.
- Directory names are bare IDs (M001, S01, T01). File names are ID-SUFFIX (M001-ROADMAP.md, S01-PLAN.md, T01-PLAN.md). Legacy descriptor-suffixed names are still resolved by prefix match.
- Milestone branches are named milestone/<MID>; manual worktrees use worktree/<name>.
- The package version (3.0.0) is semver and unrelated to milestone numbers.

## Adoption candidates (reader's)

- **Sliding-window stuck detector with named rules** (effort S; relates to F09, F10, F14). Adopt: Four named rules over the recent unit keys and errors: a repeated identical error, the same unit key three times in a row or in the window, an A-B-A-B oscillation, and the same missing file twice. Suppress the verdict while a retry backoff is still pending. Compare with Inonu's current stagnation stop first, since it may already cover some of these. In Inonu: A pure function detect_stuck(window) in the loop runner with one test per rule, plus a check that fails when a rule has no test.
- **Pure decision functions for loop control** (effort M; relates to F05, F06, F10). Adopt: Keep the loop as I/O glue. Each decision (continue, stop, retry, wait, pause, skip) is a function over plain inputs that returns a tagged result. GSD's workflow-kernel exports about 18 such functions, and each is testable without a runtime. In Inonu: A pure decision module with a returned action record per decision, table-driven tests, and a check that the loop imports decisions instead of inlining them.
- **Named, ordered dispatch rule table with first-match semantics** (effort S; relates to F08, F21). Adopt: A list of named rules per phase, where each rule returns an action or falls through, so the next unit can be explained from the rule name in the log. End the table with an explicit stop rule. In Inonu: A rules list in the decision module, a rules-listing subcommand of the Inonu CLI that prints rule names, and a test that every reachable phase ends in a rule or an explicit stop.
- **Dispatch ledger with one active claim per unit and an attempt budget** (effort M, fenced; relates to F14, F09). Adopt: Record each unit dispatch with a fencing token, attempt count, maximum attempts and next-run time. Enforce one active claim per unit with a partial unique index, so a double dispatch fails at insert. Compare with the Decision Graph's current revision model before adding a table. In Inonu: A new table in the SQLite Decision Graph with a partial unique index, a check that rejects a second active claim, and a migration recorded as a revision.
- **Database as the only writable source, with hash-checked markdown projections** (effort S; relates to F01, F05). Adopt: Keep the Decision Graph as the single writable source and render markdown views from it. Put a content hash in each rendered file, so a stale or hand-edited view is detected. GSD does this with detectStaleRenders and renderAllFromDb. In Inonu: A render command plus an audit rule in the SDD artifact audit that fails when a rendered file's hash does not match its source rows.
- **Drift catalog checked before dispatch, with capped repair passes** (effort M; relates to F06, F01). Adopt: A fixed list of drift kinds (stale render, unregistered milestone, missing completion timestamp, roadmap divergence). Each kind has an idempotent repair, the reconcile pass runs at most twice, and persistent drift stops the run with a typed error. Compare with the current SDD artifact audit, which reports but may not repair. In Inonu: An audit subcommand that lists drift findings and exits non-zero on any unrepaired drift, with an opt-in repair flag limited to derived files; repairs never rewrite decision rows without owner approval.
- **Stall-aware unit timeouts with three tiers** (effort M; relates to F11). Adopt: A soft timeout that asks for wrap-up and triggers a turn only when no tool is running; an idle watchdog that counts a stall only when a tool has been in flight past the idle window and the working tree shows no changes; a hard timeout that pauses the run. Scale windows by an estimate, capped. In Inonu: A loop-runner config with three timeouts, an idle check that reads git status for working-tree changes, a test for each tier, and the existing process-tree kill for the hard stop.
- **Crash-safe session lock with PID liveness and a stale window** (effort S; relates to F13, F15). Adopt: A lock file with the owner PID and start time. A new run treats the lock as stale only when the PID is dead or the heartbeat is past a stale window (30 minutes in GSD). Signal handlers release the lock on SIGTERM, SIGHUP and SIGINT. Use a per-milestone lock when parallel workers run. In Inonu: A lock module with acquire, release and stale-check functions, tests for a dead PID and an expired heartbeat, and a signal-handler test.
