## Summary

OpenSpec 1.15.0 at 6d04a1b keeps current behaviour in openspec/specs and proposed work in openspec/changes, one folder per change. A change holds proposal.md, optional design.md, tasks.md and delta specs using ADDED, MODIFIED, REMOVED and RENAMED sections. archive validates, merges the deltas in the order RENAMED, REMOVED, MODIFIED, ADDED, writes the specs, then moves the folder to archive/YYYY-MM-DD-name. The CLI verbs are deterministic (status, instructions, validate, archive, list, show); verify and sync are agent-run skills with no verb. Twelve workflows, 50 tool entries, Node 20.19 or later, plus Bun standalone binaries. Against Inonu: the baseline-versus-delta model is absent from Inonu, but OpenSpec verifies by prompt, where Inonu's loop runner checks deterministically. Static reading only; nothing was run.

## Lifecycle

1. **1. Initialise project** — human: openspec init (or openspec update). Inputs: project directory and --tools selection. Outputs: openspec/ with config, specs, changes and archive directories, plus generated skills or command files. Gate: openspec/config.yaml must exist for the root to be recognised (src/core/openspec-root.ts 185-186); init.ts itself was not read.
2. **2. Baseline exists** — maintained by archive or sync; humans may edit Purpose. Inputs: current spec files. Outputs: openspec/specs/<capability>/spec.md. Gate: none; read by list --specs and show --type spec.
3. **3. Create change** — human or agent: openspec new change <name> (also the new skill). Inputs: kebab-case name, optional --schema, --goal, --description. Outputs: openspec/changes/<name>/ with .openspec.yaml; README.md when a description is given. Gate: name matches the kebab grammar; folder must not exist; schema must resolve (change-utils.ts 131-168).
4. **4. Check status** — agent or human: openspec status --change <name> --json. Inputs: change folder and schema. Outputs: per-artifact done, ready, blocked or skipped. Gate: done when the generates file exists (state.ts 14-37); blocked when a requires entry is not done.
5. **5. Read artifact instructions** — agent: openspec instructions <artifact> --change <name> --json. Inputs: change, schema, project config. Outputs: context, rules, template and dependency information. Gate: blocked artifacts produce a warning rather than a refusal (instructions.ts 239).
6. **6. Author proposal, specs, design, tasks** — agent via the propose, ff or continue skills. Inputs: instructions for each artifact. Outputs: proposal.md, specs/<capability>/spec.md, design.md (optional), tasks.md. Gate: Why length 50 to 1000 characters; every requirement has a scenario; the change has deltas or skip_specs (schema.yaml 36-42).
7. **7. Validate** — human or agent: openspec validate <name> [--strict] [--json]. Inputs: change folder, delta specs and baseline specs. Outputs: ERROR, WARNING and INFO issues with paths. Gate: no ERROR; under --strict no WARNING either (validator.ts 1015-1022).
8. **8. Apply instructions** — agent: openspec instructions apply --change <name> --json. Inputs: tasks.md (from apply.tracks) and required artifacts. Outputs: state blocked, ready or all_done, with each task's sourcePath and line. Gate: blocked when tasks or the tracks file are missing (instructions.ts 638-666).
9. **9. Implement tasks** — agent (apply skill). Inputs: task list with locations. Outputs: code changes, and [x] written at the returned line. Gate: task behaviour fully implemented, by skill rule (apply-change.ts 207-210); pause on blockers.
10. **10. Verify (optional)** — agent (verify skill); no CLI verb. Inputs: status, apply instructions, specs and design. Outputs: report with CRITICAL, WARNING and SUGGESTION findings and not-verified cells. Gate: skill says fix CRITICAL before archive; enforced by prompt only (inferred).
11. **11. Sync (optional)** — agent (sync skill), or the inline sync that archive triggers. Inputs: delta specs and the specs instructions. Outputs: edited openspec/specs/*/spec.md. Gate: MODIFIED or RENAMED needs an existing spec; REMOVED-only needs retire_capabilities (archive-change.ts 133-137).
12. **12. Archive** — human or agent: openspec archive <name> [-y] [--skip-specs] [--no-validate]. Inputs: change folder, baseline specs, optional retire marker. Outputs: merged specs and openspec/changes/archive/YYYY-MM-DD-<name>/. Gate: validation clean unless --no-validate; incomplete tasks need confirmation or -y; destination must be free; merge conflicts abort (F07, F10).
13. **13. Post-archive lint** — CI or pre-commit: openspec validate --archived. Inputs: archived change folders. Outputs: failures for archived changes with unfinished tasks. Gate: every task in each archived change is completed (cli/index.ts 640-653).

## Artifacts

- `openspec/specs/<capability-path>/spec.md` — Main spec: the current behaviour of one capability, source of truth, edited by archive or sync Format: Markdown with a ## Purpose section, a ## Requirements section, ### Requirement: blocks and #### Scenario: blocks.
- `openspec/changes/<change-name>/proposal.md` — Why the change exists, what changes, and which capabilities are new or modified Format: Markdown with Why, What Changes, Capabilities (New, Modified) and Impact sections; Why must be 50 to 1000 characters.
- `openspec/changes/<change-name>/specs/<capability-path>/spec.md` — Delta for one capability: what is added, modified, removed or renamed Format: Markdown with an optional ## Purpose (new capabilities only) and ## ADDED, MODIFIED, REMOVED or RENAMED Requirements sections.
- `openspec/changes/<change-name>/design.md` — Technical approach: context, goals and non-goals, decisions, risks, optional migration and open questions Format: Markdown; created only when the schema instruction applies.
- `openspec/changes/<change-name>/tasks.md` — Implementation checklist that apply tracks and archive counts Format: Markdown: ## N. group headings, then '- [ ] N.M description' checkbox lines; optional ## Workflow follow-up bullets.
- `openspec/changes/<change-name>/.openspec.yaml` — Per-change metadata: schema, created date, goal, affected areas, skip_specs and retire_capabilities markers, x- extension keys Format: YAML; schema is required; unknown keys warn.
- `openspec/changes/archive/YYYY-MM-DD-<change-name>/` — Archived change folder, moved not copied, with its full history of artifacts and deltas Format: Same folder layout as an active change.
- `openspec/config.yaml and openspec/schemas/<name>/schema.yaml (+ templates/)` — Project configuration (schema, context, per-artifact rules) and project-local workflow schemas Format: YAML; schema templates are Markdown files.
- `.claude/commands/opsx/<id>.md (and .cursor/commands/opsx-<id>.md)` — Generated per-tool command files that invoke the workflows Format: Markdown with a YAML frontmatter block (name, description, allowed-tools, category, tags).

## Numbering rules

- Change ids are kebab-case folder names matching lowercase letters, digits and single hyphens. No sequence number exists.
- Archive folders are named YYYY-MM-DD-<change-name> using the local date. A change name that already starts with a date keeps that date.
- Task ids are N.M (optionally with trailing letters) inside '## N.' group headings. The group number must equal the id's leading number, and an id should not repeat across tracked files.
- Requirements are identified by their header name after '### Requirement:' and matched after normalising case and spacing. There are no numeric requirement ids; openspec show -r takes a 1-based index.
- Scenarios use exactly four hashes, '#### Scenario:'. Three hashes are not recognised.
- Delta section titles are fixed: ADDED Requirements, MODIFIED Requirements, REMOVED Requirements, RENAMED Requirements.
- The CLI package version is 1.15.0 (package.json).

## Adoption candidates (reader's)

- **Delta-merge conformance check for baseline and change specs** (effort M; relates to F06, F07, F11). Adopt: Keep one baseline spec per capability and per-change delta files. Check that deltas use only the four operation sections, have no duplicate or conflicting names, that MODIFIED and RENAMED targets exist in the baseline, and that every requirement has a scenario. Report ERROR and WARNING levels as JSON. In Inonu: A check in the SDD artifact audit with a JSON report and exit code, plus a docs lint rule for the four delta titles.
- **Zero-delta gate with an explicit skip marker** (effort S; relates to F09). Adopt: A change with no spec deltas fails unless its metadata declares it changes no specs. Declaring it while spec files exist is an error. This stops empty changes passing silently. In Inonu: An audit rule plus an optional metadata key in the SDD change folder, checked by check.
- **Merge in memory, validate, then write and move** (effort M; relates to F07, F12, F14, F25). Adopt: Build the merged baseline in memory, run the conformance check, and write files only when it passes. Snapshot and restore on failure. Move the finished change into a date-prefixed archive folder. In Inonu: An sdd archive --dry-run path that reuses the existing backup and rollback ledger, and a dated archive folder rule. Writes stay inside the repo's spec files, with no git history rewrite and no migration.
- **Only explicit done counts as done** (effort S; relates to F05, F04). Adopt: Count a task as done only for [x] or [X]. Treat any other marker as not done, flag a tracked file that has no checkboxes, and exclude link-style bullets. In Inonu: A deterministic parser inside the loop runner's verified_done check, and a docs lint rule for the checkbox format.
- **Three-state verdict where not-verified never passes** (effort S; relates to F23, F11). Adopt: Reviewer reports use pass, fail or not_verified per check, with CRITICAL, WARNING and SUGGESTION severities. A not_verified check blocks done. Inonu already requires every check to pass; this adds the explicit third state OpenSpec uses. In Inonu: A JSON verdict schema for reviewers, and a loop runner rule that refuses done while any check is not_verified.
- **Ready queue from declared dependencies with declaration-order ties** (effort M; relates to F02, F03, F04). Adopt: Derive readiness from declared requires lists. Break ties by declaration order. Treat an artifact or task as complete only when its concrete output path exists. In Inonu: A schema file (YAML or JSON) with artifacts as id, generates and requires, read by the decision graph ready queue, with ties broken by array index.
- **Load-time contract checks for workflow definitions** (effort S; relates to F21). Adopt: Reject duplicate ids, unknown dependency references, cycles and unknown apply references when the definition loads. Warn when a tracking path matches no output. In Inonu: A validator run by doctor and by docs lint over workflow definition files.
- **Explicit opt-in before deleting a capability spec** (effort S; relates to F10). Adopt: Allow deleting a baseline spec only when the change declares retirement and its last requirement is removed. Otherwise abort. Record the deletion in the report. In Inonu: A metadata key checked by the conformance check, and an archive step that refuses deletes without the key. Deletions stay reversible in git and do not rewrite history.
