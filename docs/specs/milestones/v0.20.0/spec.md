# v0.20.0 — A Stop hook that can actually gate

The source-level research ([research-reverse-engineering.md](research-reverse-engineering.md), gap G1) found a functional defect in the opt-in Stop hook that `bundle apply --with-stop-hook` registers. It runs `check`, which exits 1 on failure, and a Stop hook blocks only on exit 2: any other non-zero code is a non-blocking error, so the hook could never block. It also runs Inonu's own test suite in every project instead of the project's verifier, declares no timeout and has no limit on consecutive blocks. This milestone replaces it with a real hook command. The hook stays opt-in and is not installed anywhere. The scope was decided by Jev consensus ([decisions.md](decisions.md)).

## Requirements

- R1 `python -m inonu_harness hook stop [--home PATH]` is the hook command. It reads the hook's JSON from stdin (an empty or invalid body is treated as `{}`), never prints a traceback, and exits with: 0 when every check passes, when the project has no verifier config, or when the block limit is reached; 2 when a check fails (stderr carries the message the model sees); 1 for an infrastructure problem (invalid or untrusted config, unexpected error), which the host treats as non-blocking.
- R2 The project directory is `$CLAUDE_PROJECT_DIR` when set, otherwise the JSON's `cwd` when it is a string naming a directory, otherwise the process working directory. The verifier config is `.inonu/verify.json` directly inside it; ancestors are not searched. No config is a silent no-op with exit 0 and no output.
- R3 The config is strict JSON (duplicate keys, unknown keys and wrong types are invalid) of at most 64 KiB: `{"checks": [{"id": str, "argv": [str, ...]}, ...], "timeout_seconds": int, "max_consecutive_blocks": int}`. All three keys are required with no defaults; `checks` holds 1 to 20 entries with unique non-empty ids and non-empty argv lists; `timeout_seconds` is 1 to 600 and `max_consecutive_blocks` is 1 to 20.
- R4 Trust. A repository can ship that file, so the hook runs it only after the owner grants trust. `python -m inonu_harness hook trust [--root PATH] [--home PATH] [--yes]` previews (without `--yes`) or records the config's SHA-256 against its resolved path in `<home>/.inonu-harness/hook-trust.json` (atomic write). The preview lists every check id and argv so the owner can review what will run. `hook untrust [--root PATH] [--home PATH]` removes the entry. The hook reads the trust file but never writes it. A config that is not listed, or whose hash differs, exits 1 with a message that names the fix and never runs. A trust file that cannot be read or parsed also exits 1.
- R5 Execution. Checks run sequentially as argv lists without a shell, with stdin closed, in the project directory, each limited to the remaining part of one total budget of `timeout_seconds`, and the process tree of each is killed when it ends (reuse the loop runner's process-tree handling). Output is captured to a temporary file and only its last 1500 bytes per failing check are kept.
- R6 Block limit. A counter of consecutive blocks is kept in a small JSON file under the system temporary directory (`inonu-hook-state/<first 16 hex of sha256(session_id + config path)>.json`). A failure increments it; a pass resets it. When it has already reached `max_consecutive_blocks`, the hook resets the counter, writes a one-line note to stderr and exits 0, so the agent is never trapped. A missing `session_id` is treated as an empty string.
- R7 Message. On a failed check the stderr message names the attempt (`attempt N of MAX`), each failing check id with its exit code or `timed out`, a one-line instruction to fix them and try again, and each failing check's captured tail. Every tail first passes the credential-pattern scan (`secret_scan.scan`); a tail that matches is replaced by a note naming only the rule names. The whole message is at most 4000 characters (truncated with a marker).
- R8 Registration. `bundle apply --with-stop-hook` registers `<runner> hook stop` with `"timeout": 630` in place of `<runner> check`. The plan and status detect that command; an earlier registration ending in ` check` is still recognized as an Inonu hook, so it is reported or conflicted instead of duplicated. `bundle remove` reverses it by the recorded hash as before. The apply preview prints, for the hook item, one sentence saying what it does (runs the project's trusted verifier on every Stop and can block the stop).
- R9 Tests cover (temp directories only, never the real home or the real temp state): strict config parsing and every invalid case; discovery order of `CLAUDE_PROJECT_DIR`, `cwd` and the process directory; no config is silent exit 0; untrusted, drifted and unreadable trust exit 1 without running anything; trusted pass exits 0; a failing check exits 2 with the id, exit code and tail; timeout kills the process tree and reports `timed out`; the block limit then exit 0 and the counter reset; a pass resets the counter; a credential-looking tail is replaced and never printed; the 4000-character cap; bad stdin tolerated; an unexpected exception exits 1 without a traceback; `trust` preview does not write, `--yes` writes atomically, `untrust` removes; one end-to-end test through `python -m inonu_harness hook stop` with stdin JSON; the bundle registration, status, conflict and remove behavior for the new command.
- R10 Docs: `docs/hook.md` (config, trust, exit codes, limits), CHANGELOG 0.20.0, README, a skill bullet and an update to `docs/plugin.md` and `docs/hosts.md` where they describe the hook. They state that the hook runs project-supplied commands with the user's permissions only after explicit trust, that the host also applies its own cap on consecutive Stop blocks (which resets whenever a tool is called), that a pattern-scanned output tail still reaches the model, and that nothing installs the hook unless the owner runs `bundle apply --with-stop-hook --apply`. Version 0.20.0 in `__init__.py`, `pyproject.toml`, `.claude-plugin/plugin.json` and the tests.

## Out of scope

Installing the hook on the owner's host, an `stop_hook_active` special case (the block counter is the limit), ancestor config search, async or SubagentStop hooks, and agent `tools` allowlists.
